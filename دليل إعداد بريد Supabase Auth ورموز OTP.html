1. لماذا احتجنا إلى Custom SMTP؟

يقدم Supabase خادم بريد افتراضيًا للتجربة الأولية فقط. له قيود تسليم ومعدل إرسال منخفض، وليس مخصصًا للإنتاج.

منذ 3 يونيو 2026 لا تستطيع المشاريع المجانية الجديدة تعديل قوالب رسائل Auth عند استخدام مزود Supabase الافتراضي. يظهر في لوحة التحكم تنبيه يطلب إعداد Custom SMTP قبل تعديل عنوان الرسالة أو محتواها. يعود تعديل القوالب للعمل بعد ربط مزود SMTP خاص.

  • Supabase: قوالب رسائل المصادقة
  • Supabase: قائمة التحقق قبل الإنتاج

3. إعداد Gmail قبل ربطه بـ Supabase

المتطلبات
  • 1. تسجيل الدخول إلى حساب Google المخصص للإرسال.
  • 2. تفعيل التحقق بخطوتين (2-Step Verification).
  • 3. إنشاء App Password مخصص لـ Supabase.
  • 4. عدم استخدام كلمة مرور Gmail الأساسية داخل Supabase.

App Password هو رمز مخصص من Google للاستخدام مع البرامج التي تتصل بالحساب عبر SMTP. لا يظهر مجددًا بعد إنشائه عادةً، ويجب معاملته كسر.

المرجع الرسمي من Google:
Google: تسجيل الدخول باستخدام App Passwords
قواعد حماية App Password
  • لا ترسله إلى Claude أو Codex أو أي عميل ذكاء اصطناعي.
  • لا تضعه في ملف Markdown أو .env متتبع في Git.
  • لا تلتقط صورة يظهر فيها.
  • لا تضغط Reveal أثناء مشاركة الشاشة أو التقاط الصور.
  • إذا ظهر في سجل أو صورة أو محادثة، ألغِه من حساب Google وأنشئ واحدًا جديدًا.
  • تغيير كلمة مرور حساب Google يؤدي عادةً إلى إلغاء App Passwords الحالية.

6. طريقة الاختبار الآمن

  1. استخدم مشروع dev فقط.
  2. استخدم بريدًا تجريبيًا يمكنك الوصول إليه.
  3. اطلب OTP مرة واحدة.
  4. تحقق أن الرسالة تحتوي رمزًا لا رابطًا.
  5. أدخل الرمز مرة واحدة في العميل الذي بدأ عملية التسجيل.
  6. لا تطبع الرمز في السجل.
  7. لا تطبع access_token أو refresh_token أو JWT بعد نجاح التحقق.
  8. تحقق أن إعادة استخدام الرمز مرفوضة.
  9. راجع Auth Logs عند فشل التسليم.
  10. لا تكرر الإرسال بسرعة؛ احترم Minimum interval وRate Limits.

7. ما الذي حدث مع مفاتيح Supabase؟

أثناء الفحص أعاد أمر Supabase CLI مفتاح service_role القديم كاملًا في المخرجات رغم عدم استخدام --reveal. عومل ذلك كتسريب أمني، ولم يُستخدم المفتاح في أي طلب ولم يُكتب في ملف.

مسار الاحتواء الذي نُفذ على dev:
  1. نقل Edge Functions من مفاتيح Legacy إلى المفاتيح الجديدة:
    • SUPABASE_PUBLISHABLE_KEYS
    • SUPABASE_SECRET_KEYS
  2. استخدام المفتاح المسمى default من JSON البيئة.
  3. إعادة نشر الخدمات الأربع واختبارها.
  4. تعطيل Legacy JWT-based API keys (anon وservice_role) من Dashboard.
  5. عدم تدوير JWT Signing Key.
  6. التحقق بعد التعطيل:
    • get-app-config أعاد 200.
    • الخدمات التجارية دون Authorization أعادت 401 AUTH_REQUIRED.
    • الخدمات الأربع بقيت ACTIVE.
قواعد مستقبلية:
  • لا تستخدم supabase projects api-keys في جلسة مسجلة أو مخرجات مشتركة.
  • لا تعرض قيمة sb_secret_... أو service_role.
  • العميل العام يستخدم Publishable key فقط.
  • الخدمات الخلفية تستخدم Secret key فقط.
  • لا يوضع أي Secret key داخل إضافة Chrome أو Flutter أو الموقع العام.
فهم مفاتيح API الانتقال إلى Publishable وSecret keys

8. لماذا Gmail حل مؤقت فقط؟

Gmail مصمم أساسًا للبريد الشخصي، لا للبريد الآلي عالي الاعتمادية. قد تظهر مشكلات مثل:

حدود إرسال يومية أو مؤقتة.
حظر أو تعليق الحساب عند نشاط يبدو آليًا.
ضعف أدوات السجلات والتحليل مقارنة بمزودي البريد المتخصصين.
صعوبة ضبط سمعة نطاق المنتج لأن المرسل gmail.com.
عدم وجود فصل واضح بين بريد المصادقة وبريد المراسلات الشخصية.

لذلك يستخدم فقط لتجربة dev المحدودة، ثم يُستبدل قبل الإطلاق.

9. البدائل المناسبة للإنتاج

يدعم Supabase أي مزود يقدم SMTP. القائمة الرسمية غير الحصرية تشمل:

Resend Amazon SES Postmark Twilio SendGrid ZeptoMail Brevo
مقارنة عملية أولية:
المزود مناسب عندما ملاحظات
Resend تريد إعدادًا حديثًا وبسيطًا وتكاملًا واضحًا مع Supabase يدعم SMTP وتكامل Supabase؛ يتطلب نطاقًا تملكه والتحقق من DNS
Postmark الأولوية القصوى لبريد المعاملات وسرعة التسليم متخصص في البريد التشغيلي؛ راجع الأسعار الحالية
Amazon SES تتوقع حجمًا كبيرًا وتريد تكلفة منخفضة نسبياً قوي لكنه يحتاج إعداد AWS وDNS وخروجًا من Sandbox
Brevo تريد بريد معاملات مع لوحة إدارة وخيارات إضافية افحص حدود الخطة وسياسة SMTP في بلدك
SendGrid تريد مزودًا واسع الانتشار وواجهات وتقارير راجع تغيرات الخطط والحدود وسمعة الحساب
ZeptoMail تريد خدمة معاملات منفصلة عن التسويق افحص الدعم والمنطقة والتكلفة الحالية
Mailtrap تريد اختبار الرسائل والقوالب دون إرسالها لمستخدمين حقيقيين ممتاز لبيئات الاختبار، وليس البديل النهائي وحده للإنتاج
مثال Resend SMTP من توثيقه الحالي:
الحقل القيمة العامة
Host smtp.resend.com
Port SSL 465
Port STARTTLS 587
Username resend
Password API key سري من Resend
المراجع:
  • Resend: SMTP

  • Supabase: مزودو SMTP المقترحون

11. توصية مرحلية لـ HSP

الآن — dev
  • Gmail SMTP + App Password.
  • حد إرسال منخفض.
  • بريد تجريبي واحد أو عدد محدود جدًا.

12. أمر جاهز لأي عميل ذكاء اصطناعي للبحث عن المزود

انسخ الأمر التالي كما هو، وغيّر حجم الرسائل المتوقع أو اسم النطاق إذا لزم:

أريد تقرير بحث حديث ومفصل لاختيار مزود بريد معاملات Transactional Email لمشروع حضوري سمارت برو.

السياق:
- المشروع يستخدم Supabase Auth.
- تسجيل الدخول بلا كلمة مرور عبر Email OTP.
- نحتاج Custom SMTP متوافقًا رسميًا مع Supabase.
- المستخدمون المستهدفون في المملكة العربية السعودية.
- الرسائل الأساسية: تأكيد التسجيل، رمز الدخول OTP، استعادة الحساب، وتغييرات الأمان.
- الحجم الأولي المتوقع: أقل من 10,000 رسالة شهريًا، مع قابلية النمو.
- Gmail SMTP مستخدم مؤقتًا في dev فقط، ويجب عدم اعتماده للإنتاج.
- نريد استخدام نطاق فرعي مخصص لبريد المصادقة مثل auth.example.com.

ابحث في المصادر الرسمية الحالية فقط، ولا تعتمد على معلومات الأسعار أو الحدود المحفوظة في ذاكرتك. تحقق من تاريخ كل مصدر.
